Contribution guide

Add Python tools

Expose an importable Python tool when the operation belongs in the Gateway runtime. Use MCP when it should remain a separate service.

Application 2.2.0-dev / Source-backed guide
On this page1. Package an internal tool2. Install and configure3. Add external tools4. Design a useful data tool contract5. VerifySource references

1. Package an internal tool

Put team-owned implementations in a separately versioned package. A LangChain tool supplies its own name, description and parameter schema. This pure-function example has no database access or credentials:

telecom_tools/catalog.py · illustrative convention
from langchain.tools import tool

@tool
def normalize_site_id(site_id: str) -> str:
    """Normalize our demo site identifiers by trimming space and uppercasing."""
    normalized = site_id.strip().upper()
    if not normalized:
        raise ValueError("site_id must not be empty")
    return normalized

Declare LangChain and every dependency you import in the package metadata. Test the operation directly, including invalid inputs. This normalization rule is an example, not a universal telecom identifier definition.

2. Install and configure

Install the reviewed package into the backend environment and lock its version. For a local package, an operator can run uv add /absolute/path/to/telecom-tools from backend/. Production images must include the same dependency. Add both a group and a tool entry to the root configuration:

YAML · config.yaml fragment
# Append to existing lists; preserve the built-in tools and groups.
tool_groups:
  - name: telecom

tools:
  - name: normalize_site_id
    group: telecom
    use: telecom_tools.catalog:normalize_site_id

Unlike some older documentation snippets, the current ToolConfig requires name, group and use. The imported object should have the same tool name. Arbitrary extra configuration keys do not automatically become arguments to your function; follow an established provider pattern if the tool needs configured clients.

Set a custom agent’s tool_groups to include telecom. Restart after installing/changing Python code, then test a new run. Config edits do not install packages or reload imported module code.

3. Add external tools

For an external Python package, use exactly the same dependency and class-path approach after reviewing and pinning it. For a vendor’s remote API, prefer an authenticated MCP service when you want independent deployment and a cleaner service boundary.

The checkout also contains community integrations for search, fetching, knowledge retrieval and other services. Select the provider’s existing use path and declared optional dependencies from config.example.yaml. Some providers require API keys; none become usable solely because their module exists.

4. Design a useful data tool contract

  1. Use explicit parameters such as approved metric ID, site IDs, time bounds and result limit.
  2. Enforce data permissions inside the execution service using trusted identity. An agent’s group selection is not a database access grant.
  3. Return the result grain, source tables, schema/metric revisions, query/job ID, row count and freshness alongside the result.
  4. Keep credentials and unrestricted administrative operations out of the model-visible schema and outputs.
  5. Use async I/O for network services and cancellation-aware timeouts. Package side effects with idempotency where supported.

5. Verify

For the demo tool, ask “Normalize site identifier dal-104 .” Confirm DAL-104, then test an empty identifier. Confirm a custom agent without the telecom group cannot select this configured tool. For real data tools, validate result contracts and resource policy with authorized and unauthorized users.
