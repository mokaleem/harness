1. Author an internal skill package

Start with a narrowly defined outcome: investigate a site’s performance using approved metrics and joins. Keep the description specific enough for discovery. The supported package has a root SKILL.md saved as UTF-8.

Package layout
site-performance-review/
├── SKILL.md
├── references/
│   └── approved-metrics.md
├── scripts/
│   └── summarize_results.py
└── templates/
    └── report.md
SKILL.md · illustrative workflow
---
name: site-performance-review
description: Investigate site_id and gnodeb_id performance for a requested time window using approved telecom metrics and joins.
license: Proprietary
---

# Site performance review

1. Resolve the requested site and time window. State the timezone.
2. Read references/approved-metrics.md before selecting metrics.
3. Use the configured data tools to obtain the approved schema and join definitions.
4. Query aggregate performance with explicit time and site filters.
5. Check missing intervals, duplicate join keys and result grain.
6. Report the metric definition, data freshness, query evidence and limitations.
7. Save the report to /mnt/user-data/outputs/ and present the artifact.

Do not invent a relationship between site_id, fuze_site_id and gnodeb_id.
Request a validated mapping when the catalog does not define one.

A skill does not install an MCP server or make a database connection merely by mentioning one. Provision required tools and sandbox dependencies separately. Supporting scripts must be available in the sandbox and have their Python/system dependencies installed there.

Optional frontmatter includes allowed-tools, required-secrets, secrets-autonomous, compatibility and descriptive metadata. Use actual runtime tool names when specifying allowed-tools; this narrows an activated workflow and does not grant access to otherwise denied tools.

2. Install with the correct ownership

ScopeInstallation routeBehavior
One userUpload an archive through the skill installer or use the embedded clientCustom skill content and enabled state are user-scoped. Gateway installation requires administrator access.
Deployment public bundleOperator places a reviewed package beneath the configured skills/public/ rootGlobal, read-only through user editing surfaces; include it in the deployed image or volume.
Managed integrationUse the capability/integration installation flow for that providerManaged pack under runtime integrations; credentials and enabled integration state remain per user.
Legacy shared custom directoryskills/custom/ at the global rootRead-only fallback for users without their own custom skill directory; do not treat this as the current team publication API.

The runtime home defaults to .deer-flow under the project root unless DEER_FLOW_HOME overrides it. User custom packages live under {runtime_home}/users/{user_id}/skills/custom/. Public skills come from the configured host skill root. Let the installer own user paths rather than guessing identity values.

Build a .skill file as a ZIP archive. This command runs from the parent of the package folder:

Python · archive creation
from pathlib import Path
from zipfile import ZIP_DEFLATED, ZipFile

package = Path("site-performance-review")
with ZipFile("site-performance-review.skill", "w", ZIP_DEFLATED) as archive:
    for file in sorted(package.rglob("*")):
        if file.is_file():
            archive.write(file, file.relative_to(package.parent).as_posix())

Use the Skills settings upload control, or send authenticated multipart POST /api/skills/install/upload with file field archive. The filename must end in .skill. A skill produced in an existing thread can instead use POST /api/skills/install:

JSON · thread archive installation body
{"thread_id": "your-thread-id", "path": "/mnt/user-data/outputs/site-performance-review.skill"}

3. Import an external skill

  1. Obtain a reviewed release or pinned repository revision from its owner. The skill installer does not accept an arbitrary GitHub URL as its request body.
  2. Find the actual skill root, including SKILL.md and required supporting files. Check the license and replace vendor-specific tools, URLs or path assumptions.
  3. Package that directory as a .skill archive and use the same installation flow above. Imported third-party skills normally become the caller’s custom skills; source origin does not make them managed integration packs.
  4. Provide dependencies and credentials through the supported execution environment. Keep secrets out of skill text and archives.
  5. Use the read-only skill reviewer to inspect quality and resource references. Installation/evolution scanning is separate from this quality review; neither proves the workflow is correct.

4. Enable, select and activate

Inspect GET /api/skills. Administrators can toggle with PUT /api/skills/site-performance-review and {"enabled": true}. Public state is global; custom state is per user. Select the skill in the custom agent’s skills list, then explicitly request /site-performance-review in a test conversation.

YAML · optional metadata discovery
# Merge into the root config.yaml.
skills:
  container_path: /mnt/skills
  deferred_discovery: true

Deferred discovery exposes names first and details through describe_skill. It is separate from tool_search.enabled. Discovery does not activate a skill’s tool policy. Explicit activation or loading its file establishes active context.

After operator file edits, POST /api/skills/reload invalidates the current Gateway process’s caches. It is not a fleet-wide reload. The next run must see the refreshed skill projection; follow your deployment rollout procedure across workers.

5. Verify the workflow

  1. Confirm the package appears for the intended user and is absent from unrelated users’ custom catalogs.
  2. Check a normal site, an unknown site, an empty result window and an ambiguous site-to-RAN mapping.
  3. Verify tool availability, approved joins, query/result evidence and artifact delivery.
  4. Confirm scripts run inside the selected sandbox and no secret is embedded in the exported package.
Optional: agent-created skills
YAML · opt-in
skill_evolution:
  enabled: true
  security_fail_closed: true

This exposes skill_manage for user custom creation/editing with scanning and history. It does not provide enterprise-wide review or publication. See the bundle-promotion design.
