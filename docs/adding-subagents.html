Add subagents

Add internal and external specialist workers, using native subagents or a supported integration with a separately running agent.

Internal and external subagents

OriginNative workerSeparately running specialist
InternalYour team’s metrics reviewer in the managed subagent catalogA corporate specialist service reached by an approved MCP/tool adapter, or an internal ACP process.
ExternalA vendor-authored worker definition installed in the same native catalogA vendor specialist reached through MCP/tool integration or a compatible ACP process.

A subagent is a delegated role, not an ownership category. A vendor-authored native definition follows native task semantics. A separately running internal agent follows its protocol’s semantics. ACP and service calls are not automatically members of the native task catalog.

1. Add an internal native worker

Native workers share the DeerFlow execution framework. Built-in types are general-purpose and bash; host bash availability depends on sandbox policy. Add a specialist through administrator Settings → Subagents or authenticated POST /api/subagents:

JSON · managed subagent creation body
{
  "name": "ran-metrics-reviewer",
  "display_name": "RAN Metrics Reviewer",
  "description": "Validate site and gNodeB metric grain, approved joins and missing intervals.",
  "system_prompt": "Review supplied performance evidence. State grain, cardinality, freshness and uncertainty. Never invent joins. Return a concise evidence-based result to the lead agent.",
  "skills": ["site-performance-review"],
  "model": "inherit",
  "max_turns": 30,
  "timeout_seconds": 300,
  "enabled": true
}

Managed definitions are deployment-wide. File storage uses {runtime_home}/managed-subagents/; agent_storage.backend: db uses the shared application database. Only administrators create/update/delete; ordinary listing hides system prompts from non-administrators.

Alternatively, an operator can declare the worker in root configuration. Do not create a managed worker with a name already reserved by a built-in/configured definition:

YAML · alternative operator definition
subagents:
  custom_agents:
    ran-metrics-reviewer:
      description: Validate site and gNodeB performance evidence.
      system_prompt: >-
        Check approved joins, result grain and missing intervals.
        Return conclusions and evidence to the lead agent.
      skills: [site-performance-review]
      model: inherit
      max_turns: 30
      timeout_seconds: 300

tools accepts actual tool names, not group names. Omitted/null inherits eligible tools; an empty list selects none. disallowed_tools further narrows selection. Managed workers always merge denial of task, ask_clarification and present_files; the lead owns delegation and user delivery.

2. Enable and test delegation

  1. Use Ultra mode in the chat input, which enables subagent delegation. For an embedded client, pass subagent_enabled=True.
  2. If using a custom agent, include ran-metrics-reviewer in its allowed_subagents.
  3. Send a task with a clear independent review step, such as “Have the RAN metrics reviewer validate this performance result before summarizing it.”
  4. Check the task card, selected subagent_type, result and termination status. Ask the lead to deliver final artifacts.
  5. Test timeouts, cancellation, denied tools and the shared execution-capacity limit.

Descriptions guide the lead’s choice; they do not guarantee deterministic routing. Skill selection makes metadata available; instructions/tool policies take effect when the skill is loaded or activated.

3. Add an externally supplied worker

Vendor-authored native definition

Review its instructions and capabilities, then use the same managed subagent API or operator configuration shown above. Vendor origin does not require ACP. A native worker can also call a separately running specialist through a narrowly selected tool:

JSON · POST /api/subagents, service-backed native worker
{
  "name": "vendor-assisted-ran-reviewer",
  "description": "Delegate approved RAN analysis to the installed vendor service and check its evidence.",
  "system_prompt": "Use the selected vendor tool for the delegated task. Return its evidence, uncertainties and failure status to the lead. Do not invent successful results.",
  "tools": ["vendor-ran-analyzer_analyze_site"],
  "skills": [],
  "model": "inherit",
  "max_turns": 20,
  "timeout_seconds": 300,
  "enabled": true
}

The tool name is illustrative: install the vendor MCP from the MCP guide and replace it with its actual discovered tool. Ensure the parent agent can access that installation and add this worker to its native allowed_subagents. The same wrapper approach applies to an internal corporate service using its own tool name. Native worker limits apply to the wrapper; remote execution and cancellation guarantees still depend on the service contract.

Internal or external ACP process

A third-party or internal CLI can be used if it speaks Agent Client Protocol. Install its reviewed ACP-compatible executable in the Gateway environment, then configure it:

YAML · illustrative installed ACP executable
acp_agents:
  vendor-reviewer:
    command: /opt/vendor-reviewer/bin/vendor-reviewer-acp
    args: []
    description: Review a supplied telecom analysis and return supporting evidence.
    env:
      VENDOR_API_KEY: $VENDOR_API_KEY
    auto_approve_permissions: false
    timeout_seconds: 300

The executable above is a placeholder for your installed compatible agent. This checkout’s example configuration also documents ACP adapters for third-party coding CLIs. Plain CLI commands are not automatically ACP-compatible.

Once configured, the lead uses invoke_acp_agent with agent name vendor-reviewer and a self-contained prompt. The subprocess has its own workspace; do not pass /mnt/user-data paths as if it shared the lead’s sandbox. Outputs are exposed at /mnt/acp-workspace/ as supported by the provider; the lead copies deliverables into its outputs area.

Different runtime contract. ACP calls do not use the native task catalog, native capacity control or native task ledger. allowed_subagents governs native workers, not an ACP installation. With auto_approve_permissions: false, every ACP permission request is denied; there is no interactive permission prompt. Setting it true auto-approves requests. ACP execution is a host subprocess, not automatically a DeerFlow sandbox.

For remote agent services, use a reviewed MCP/tool adapter with explicit identity, timeout and result semantics.

4. Choose the correct durability mode

ModeUse caseDurability boundary
Native taskOne specialist review inside a lead runOrdinary subagent graph has no checkpointer; do not assume restart resumption.
Native batch_taskMany independent site investigationsPersistent item repository, leases, retries and acceptance checks; requires enabled batch runtime and database.
ACP invoke_acp_agentIndependent compatible external processIts own timeout/workspace contract; separate from native batch guarantees.
MCP background taskVendor/service-owned asynchronous reportConfigured task toolset, tracking repository and notifications; separate service semantics.
YAML · opt-in durable batch runtime
# Requires configured database backend sqlite or postgres.
subagent_batches:
  enabled: true

Batch runtime is startup-configured; restart after enabling it. Worker retries do not make external side effects exactly-once. Use idempotent operations and test recovery. Native subagents share the thread workspace, so a skills allowlist is not a separate per-worker filesystem security sandbox.
