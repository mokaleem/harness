Add agents

Add internally owned and externally supplied agents, either as native configurations or independently running services/processes.

Internal and external agents

OriginRuns inside DeerFlowRuns separately
InternalYour team’s RAN Analyst configuration and SOUL.mdA corporate NOC agent accessed through MCP, a tool adapter or a compatible ACP process.
ExternalReviewed vendor-authored instructions recreated as a custom agentA vendor agent accessed through its supported MCP/tool interface or compatible ACP process.

Native versus separately running is a runtime choice, independent of internal versus external ownership. A custom agent is an identity/configuration inside DeerFlow; registering one does not automatically connect a remote agent service.

1. Create an internal custom agent

A custom agent combines a configuration with SOUL.md instructions. It reuses the Lead Agent runtime and middleware. It is not a new Python harness.

The custom-agent management API is disabled by default. An operator must enable it, then use an authorized authenticated account:

YAML · config.yaml
agents_api:
  enabled: true

Use the workspace Agents creation flow or POST /api/agents. The JSON below is a request body; the referenced model, skill and subagent must already exist:

JSON · POST /api/agents request body
{
  "name": "ran-analyst",
  "display_name": "RAN Analyst",
  "description": "Investigates site and gNodeB performance using approved definitions.",
  "skills": ["site-performance-review"],
  "allowed_subagents": ["ran-metrics-reviewer"],
  "soul": "You are a RAN analyst. State definitions, time bounds, grain and evidence. Never infer undocumented joins."
}

Name characters are letters, digits and hyphens; names are stored lowercase. Agents are user-owned in the current storage model. With file storage, they live under {runtime_home}/users/{user_id}/agents/{name}/; database storage uses the corresponding repository. Use supported management surfaces rather than assuming file paths under database storage.

Stored AgentConfig also supports memory_enabled, but the current creation/update HTTP request schemas do not expose that field. Do not assume every stored setting can be sent through the API.

2. Select capabilities deliberately

FieldMeaning
modelA configured model name; omitted/null inherits the runtime choice.
tool_groupsConfigured tool group selection. Preserve necessary sandbox groups when narrowing access.
skillsOmitted/null = enabled visible skills; empty list = none; list = selected skills.
mcp_pluginsStable MCP installation IDs; null = inherit; empty list = none. Obtain actual installation IDs.
allowed_subagentsNull = enabled catalog; empty list = no native delegation; list = selected types.
knowledge_scopeDefault supported knowledge-retrieval scope; not a general database join catalog.
model_settings, thinking_enabled, reasoning_effortModel behavior defaults and supported per-agent overrides.

Selection narrows what the agent can use. It does not replace user authorization or grant remote database permissions. An allowlist cannot make an unavailable installation or skill appear.

3. Add an externally supplied agent

External contributionSupported approach
Instructions/configuration authored by another teamReview the instructions and recreate a user-owned custom agent with existing local capabilities. No universal external-agent archive importer is assumed.
A process speaking Agent Client ProtocolRegister it under acp_agents; invoke through invoke_acp_agent. See the external-process recipe below.
A remote agent service exposing MCP toolsRegister its MCP service and define a bounded task/result tool contract.
An arbitrary HTTP agent APIImplement a reviewed tool/MCP adapter for that API; a URL alone is not a native subagent definition.

Vendor-authored native agent

  1. Review the supplied agent instructions/configuration and required tools.
  2. Create a new custom agent through the same POST /api/agents flow, using the reviewed instructions as soul.
  3. Map every referenced model, skill, MCP installation and subagent to an installed local capability. Select its permitted scope and test it under the owning user.

Internal or external independently running agent

  1. Identify the actual interface: a supported MCP endpoint, an HTTP API requiring a tool adapter, or an ACP-compatible executable.
  2. For MCP, follow internal server setup or external server setup. Define bounded task inputs and result/evidence outputs.
  3. For ACP, follow the process setup recipe. An internal corporate executable uses the same mechanism as a vendor executable.
  4. Test identity propagation, task failure, timeout and result handling before allowing the lead to invoke it.

ACP is Agent Client Protocol in this implementation. A remote HTTP URL does not by itself become a native agent registration; it needs the corresponding integration.

4. Use and verify the agent

  1. Select RAN Analyst in the Agents workspace and start its conversation.
  2. Ask for a site-performance review. Confirm the right skill and approved tools are available.
  3. Enable Ultra mode if native delegation is needed; the custom-agent subagent allowlist still applies.
  4. Test an unknown site, missing join and unavailable selected model/tool.
  5. Confirm another user cannot read or alter this user-owned agent through its management endpoints.
Python · embedded usage
from deerflow.client import DeerFlowClient

# Run in the configured backend environment.
client = DeerFlowClient(agent_name="ran-analyst", subagent_enabled=True)
answer = client.chat("Review the available site-performance evidence.", thread_id="ran-review-001")
print(answer)

The example needs the same effective user’s agent/configuration and does not inject a browser session. Supply a compatible checkpointer for persistent multi-turn embedded conversations; the client is stateless without one.
